# 页面文案规范：空态、滞后与停更

> 2026-11-13 定稿，基线 `dcf2695`。本文是**可直接抄进代码的字符串**，
> 不是原则探讨。每条给出「触发条件（精确到字段）」+「文案原文」+「禁止用词」。
>
> 适用范围：市场数据（`/scene/market`）、分时研究（`/scene/intraday-research`）、
> 预测复盘（`/scene/review`）、策略反演停用页（`/scene/inference`）。

## 0. 三条总原则（违背了下面任何一条，文案就是错的）

1. **永久缺失不许写成临时状态。** 「暂无数据」「加载中」暗示等一会儿会有。
   通道已停更、留痕尚未积累，都是**不会再自己变好**的，必须说死。
   （唯一例外：官方 T+2 的「实际值还没出」是真的等一会儿就有，可以正常口气。）
2. **日期只写具体日期，不写「实时」「最新」。** 三源节奏不同（T+0 / T+2 / T-6），
   任何「最新」都在制造一个假的统一时间点。
3. **语气跟严重性对齐。** 等人、等源站发布 = 中性；要人动手排查 = 告警。
   把「等就行」写成红色，会让人去修一个没坏的东西；把「坏了」写成中性，就没人修。

## 1. 市场总览 · 24 点分时

数据源 `gd_home_24h`，接口 `/api/gd-metric/home-24h`，状态字段取自
`/api/gd-metric/home-market/status` 的 `home24h`。
正常滞后 T-6（`expectedLagHome24h = 8`，超 8 天才算 lagging）。

| # | 场景 | 触发条件（代码字段） | 文案原文（可直接粘贴） | 呈现 | 禁止用词 |
|---|---|---|---|---|---|
| 1.1 | 缺点日 | `pointCount !== 24`（恒等 `HOME24H_POINTS_PER_DAY`），且 `!empty` | 面板页脚：`仅 ${pointCount}/24 点，均价与峰谷不计算（缺点日不冒充全天）` | 中性页脚，**不是告警** | 「数据异常」「部分数据」 |
| 1.2 | `never` | `state === 'never'`（`asOf === ''`） | `从未采集成功，请检查采集配置` | 告警 | 「暂无数据」「等待采集」 |
| 1.3 | `failed` | `state === 'failed'`，`errorKind ∈ {blocked, network, parse}` | `采集失败：${errorKindLabel}，最近一次成功是 ${fetchedAt \| '—'}`<br>`errorKindLabel`：`blocked`→`被源站拦截`、`network`→`网络异常`、`parse`→`数据解析失败` | 告警 | 只写「采集失败」不分类（三种处置完全不同） |
| 1.4 | `lagging` | `state === 'lagging'`（`lagDays > 8`） | `采集已落后：库里最新到 ${asOf}（${lagDays} 天前），超出正常滞后，请检查采集是否在跑` | **告警**（见下方语义说明） | 「等下一轮采集」「源站还没发布」 |
| 1.5 | `stopped` | `state === 'stopped'`（连续 3 次 `200` + 空） | `源站已连续 3 次返回空数据，疑似停更或页面改版` | 告警 | 「暂无数据」「稍后重试」 |
| 1.6 | `ok` | `state === 'ok'` | **不出任何提示** | — | 有数还说话就是噪音 |
| 1.7 | 状态接口自身失败 | `fetchMarketStatus()` 抛错，`marketStatus === null` | 退回：`该日无数据：主页 24 点滞后约 6 天才发布，库里最新到 ${latestDate \| '（还没有任何数据）'}` | 中性 | 整页白屏（禁止） |

**1.4 的语义必须说清，这是本批最容易写反的一条。**
`application/internal/logic/homemarket/status.go:22-25` 原文：「源站 T-6 才有数，给到 8 天，
**超了就是「采集没跟上」而不是「源站还没发布」**」。正常滞后落在 `ok` 里根本不弹提示，
所以能进 `lagging` 的一定是异常。「等下一轮」会让人一直等一个不会自己好的东西。

| 2.3 | `lagging` | `state === 'lagging'`（`lagDays > 2`） | `采集已落后：库里最新到 ${asOf}（${lagDays} 天前），超出正常滞后，请检查采集是否在跑` | 告警 | 「等下一轮」 |

## 3. 市场总览 · 日频指标

数据源 `gd_spot_metric`，接口 `/api/spot-market/board`。
**官方 T+2 是正常节奏，不是故障** —— 这是本节唯一的难点。

| # | 场景 | 触发条件 | 文案原文 | 呈现 | 禁止用词 |
|---|---|---|---|---|---|
| 3.1 | 该日无数据（T+2 内） | `dailyEmpty === true` 且 `lagOf(daily.date) <= 2` | `该日无数据：披露接口还没有这一天的指标（实时 T+2 才发布）。库里最新运行日 ${daily.date}` | 中性 | 「数据缺失」「异常」 |
| 3.2 | 超出 T+2 | `lagOf(daily.date) > 2` 且 `<= 7` | `采集滞后：库里最新运行日 ${daily.date}（${lag} 天前），官方正常 T+2，已超出预期` | 中性偏提醒（**不是红色**） | 「故障」 |
| 3.3 | 超过 7 天 | `lagOf(daily.date) > 7` | `采集已落后：库里最新运行日 ${daily.date}（${lag} 天前），请检查采集是否在跑` | 告警 | 「等下一轮」 |
| 3.4 | KPI 提示 | 常驻 | `实时加权均价` 卡 hint：`运行日 ${period}（实时 T+2）` | — | 「最新」「实时更新」 |
| 3.5 | 区间图空态 | `dailyEmpty && 区间查询` | `该区间无数据（披露接口还没有落库）。` | 中性 | 「暂无数据」 |

**「滞后 2 天属正常」怎么写才不像故障**：不说「滞后」，说**「官方 T+2 才发布」**——
把滞后归因到发布节奏，读者就不会去怀疑系统。只有在超过 T+2 之后才用「滞后」这个词。

## 11. 禁止用词清单（收口）

| 禁止 | 为什么 | 换成 |
|---|---|---|
| `暂无数据` | 暗示等一会儿会有，而永久缺失不会 | 说死原因与日期：`通道已停更，数据止于 2026-10-02` |
| `未接入` / `该市场未接入` | 前提错误：`typeId` 21/22 两市场都接过，不存在「没接」 | `通道已停更，数据止于 ${date}` |
| `实时` / `最新` / `实时更新` | 三源节奏不同，任何单一「最新」都是假时间点 | 具体日期 `截至 2026-11-13` |
| `加载中`（用于永久缺失时） | 永久缺失不会加载完 | 只在真 loading 用；缺失说原因 |
| `数据异常` | 零信息量，用户不知道下一步做什么 | 分类：被源站拦截 / 网络异常 / 数据解析失败，并给「最近一次成功是 X」 |
| `等下一轮采集`（用于 `lagging`） | `lagging` 是采集没跟上，等不会好 | `请检查采集是否在跑` |
| `稍后重试`（用于 `stopped`） | 连续 3 次空，重试也是空 | `疑似停更或页面改版` |
| `该日无数据`（单独出现，无原因） | 只说现象不说原因 | 带归因：`主页 24 点滞后约 6 天才发布` |

## 12. 实时 96 点（typeId=22）：建议**补展示**

**结论：补，但只补在分时研究页，作为可切换的第二条腿；不进复盘默认口径。**

依据（实测 `gd_metric.csv`，5.2 万行）：

- `typeId=22`（实时电价）的实际值共 **33,788 条**，覆盖 **352 天**，
  最近连续 **335 天**（2025-11-02 ~ 2026-10-02），默认 7 天窗口内每天 96 点齐全。
- 对比 `typeId=22` 的预测占位有 141,717 条 —— 实际值只占 19%，
  说明**不能用「有 22 就算有数」判断**，必须仍按「实际值 + 排除 999 占位」取数
  （`GetFrozenRealSeriesReadOnly` 已经这么做了）。

现状：`research/intraday.go:110` 只取 `KindDayAhead`，`KindRealtime` 有定义
（`series.go:22`）但**没有任何页面调用**。用户看不到实时 96 点，会以为它不存在。

**落法**：

| 项 | 建议 |
|---|---|
| 位置 | `/scene/intraday-research`，图上方加一个切换：`日前电价` / `实时电价` |
| 名称 | 面板标题随切换变：`96 点日前电价` / `96 点实时电价`；图例不变 |
| 接口 | `/api/research/intraday` 加 `kind` 参数（默认 `dayAhead`，与现状完全兼容），
后端把 `KindDayAhead` 换成 `NormalizeKind(kind)` |
| 角标 | 两者都保留 `第三方 · 非官方` + `已停更` —— 实时腿和日前腿同源同停更日，不能只标一个 |
| 默认 | 默认仍是 `日前电价`（现状不变，老书签不受影响） |
| 禁止 | 不让实时腿进复盘页、不进 MAE —— 复盘口径已定死为官方日频日均价 |

**为什么值得补**：这条腿的数据已经在库里（335 天连续），只差一个参数与一个切换；
零新增采集成本。展示它能让「本站到底有什么」自洽，也让日后接官方 96 点时
两条腿的容器已经就位。

## 14. 一处已撤回的错误结论（落地前请先读这段）

本文档在交付说明里曾给出过一条「`status.go:127` 是 PHP 风格写进 Go 的 bug，应改成 Go layout」的建议。**该结论错误，已撤回，不要照做。**

`lastOK.LastOkAt` 的类型是 `*gtime.Time`（gf 框架），它的 `Format` 方法是 PHP 风格，不是标准库的 reference layout：

```go
Format("Y-m-d H:i:s")         -> "2026-11-13 18:51:35"   // 正确
Format("2006-01-02 15:04:05") -> "2006-01-02 15:04:05"   // 错误，且不报错
```

影响面：§1.3 / §2.2 的 `最近一次成功是 ${fetchedAt}` 依赖这个字段。如果按错误建议改成 Go layout，页面会把字面的 `2006-01-02 15:04:05` 当成时间印出来，而且测试全绿（原断言只查非空）。

现在的护栏：`homemarket/status_db_test.go` 断言 `fetchedAt` 不得等于任一格式串本身，改回 Go layout 会立刻红（PR #154）。**§1.3 / §2.2 的文案可以直接照抄，字段本身是对的。**

## 15. `never` 吞掉 `stopped`：全新环境里「源站改版」会被说成「采集配置没配好」

实测（走 `CollectHome24h` 真实采集路径 + HTTP 桩，2026-11-13）：

**库里有历史数** → 源站连续回 `200`+空：第 3 轮变 `stopped`，符合预期。

**库是空的**（全新部署、或换了 DSN 还没采过数）→ 源站连续回 `200`+空：**5 轮之后仍然是 `never`**，`consecutiveEmpties` 已经涨到 5。

原因在 `status.go` 的判定顺序：

```go
case asOf == "":
    st.State = StateNever                 // 先命中，直接短路
case last.ConsecutiveEmpties >= stoppedEmptyRounds:
    st.State = StateStopped               // 永远走不到
```

`asOf == ""` 是「库里一条数都没有」，而 `ConsecutiveEmpties` 是「源站连续回了多少次空」——两件完全不同的事。全新环境里源站一旦改版，用户看到的是 §1.2 的「从未采集成功，请检查采集配置」，去查配置，而真实原因是源站改版。

**建议改判定顺序**（后端改动，不在本文档落地）：

| 现状顺序 | 建议顺序 |
|---|---|
| `failed` → `never` → `stopped` → `lagging` | `failed` → **`stopped`** → `never` → `lagging` |

改完之后，全新环境第一次遇到源站改版会直接说 §1.5 的话，两句都成立时优先说信息量更大的那句。

**在这条改掉之前**，§1.2 的文案照抄时补一句兜底：

| 场景 | 触发 | 文案 |
|---|---|---|
| 1.2' | `state === 'never'` 且 `consecutiveEmpties > 0`（前端拿不到这个字段时可不做） | `从未采集成功，源站最近连续 ${n} 次返回空数据 —— 优先确认源站是否改版，其次看采集配置` |

**前端目前拿不到 `consecutiveEmpties`**：`DatasetStatus`（`homemarket/status.go` 的 DTO，前端 `api/homemarket.ts` 同构）只下发 `state / asOf / lagDays / rows / rowsExpected / fetchedAt / lastError / errorKind`，没有这个计数字段。所以 1.2' 现在做不了，实际可选只有两条：

- 后端把 `stopped` 判定提到 `never` 前面（推荐，一处顺序改动，前端零改动）；
- 或者后端在 DTO 里加 `consecutiveEmpties`，前端再按 1.2' 分叉。

在任一落地之前，新环境遇到源站改版会一直误报 §1.2 的「请检查采集配置」——这是本规范里**唯一一条已知会误导用户当前排期下的行为**。
