# Design Document

# 结论：模板是稳定的

同一栏目（广东电力交易中心）的日报版式在多次采集间稳定。三篇实测（2026-09-21 / 09-19 / 09-18，前两篇 2381×3367，第三篇 1587×2245）在同一天的各页里，OCR 文本行的**归一化坐标**（中心 x/y 除以页宽/高）误差 ±0.001。因此模板全部用相对坐标表达，与分辨率无关，也不需要针对图片尺寸做分支。

  y0.681 （一）日前申报信息

# 提取算法

四步，全部基于 OCR 的行级 bbox，不依赖图像像素分析：

1. **坐标归一化**：每行取中心点除以页宽/高。页面尺寸取自日报档案里的图片宽高，缺失时用 OCR 结果包围盒推算。
2. **列校准（数据驱动）**：把表格数据行的行内碎片按中心 x 聚类成列（容差 0.022）；把文本形如 `HH:MM` 的列识别为「时刻子列」并归属其左侧数值列；最后把该表的表头名按 x 顺序配给数值列。
   之所以不用硬编码列中心：两张成交表的列中心差约 0.03（page2 与 page4 表格宽度不同），且带时刻的列其表头居中在整格上、数值偏左，硬编码会错位。
3. **行切分**：最左列（中心 x < 0.28）作为行标签；多行标签（`零价及以` + `下`）按 y 间距 < 0.020 合并（行距 0.0265，阈值必须小于它）。行标签去空白后与常量对齐（OCR 常输出「报价 600以上」）。
4. **单元格碎片合并**：同一格内按 y 拼接；若已拼接文本的括号未闭合则强制续接，修复 `36680.1798(33.92%,-0.` + `7%)` 这类跨行断裂。
5. **语义解析**：价格类 → 值 + `(±x%)` 环比；容量类 → 值 + `(占比%,环比%)`；最高/最低电价附带出现时刻。

# 校验

三条相互独立的交叉校验，任一不通过即产出可读告警（状态置为 partial）：

1. 正文 ↔ 表1(二)：`发电侧平均电价 == 日前加权平均电价`、燃煤/燃气均价分别与表1(二) 对应行相等（正文只保留 1 位小数，容差取 0.05 或相对 0.1%）。
2. 单调性：同一对象 `最高电价 ≥ 平均电价 ≥ 最低电价`。
3. 跨日报：表2(一)（滞后运行日）与该运行日已采集日报的表1(二) 逐值比较。

另有低置信度告警：单元格 OCR 置信度 < 0.8 时提示原文，便于人工复核。

# 存储

```sql
gd_spot_metric(          -- 指标长表
  report_date,           -- 日报日
  run_date,              -- 运行日（表2 为 T-2）
  dataset, scope, metric,
  value, unit, at_time,
  mom_pct, share_pct,
  source, conf, extractor_version,
  UNIQUE (report_date, run_date, dataset, scope, metric)
)
gd_spot_extract_run(     -- 每次解析的运行记录
  report_date UNIQUE, status, ocr_model, page_count, ocr_ms,
  warnings, payload, extractor_version
)
```

`report_date` 与 `run_date` 必须分开：表2 的数据属于 T-2 运行日却来自 T 的日报。

唯一键含 `report_date`（指标归属产出它的那份日报）。初版把唯一键放在 (run_date, dataset, scope, metric)，上线即失败：09-19 的日前成交电价既由 09-19 日报的表1(二) 产出，也已由 09-21 日报的表2(一) 产出，后一次提取必然撞唯一键。改为含 report_date 后两份日报各自成行，数值由跨日报校验保证一致；按运行日聚合（趋势、交叉校验）时优先取 `source=表1(二)` 的行，忽略滞后来源。

数据集取值：`summary`（正文摘要）、`day_ahead_decl`（表1(一)）、`day_ahead_trade`（表1(二)/表2(一)）、`realtime_trade`（表2(二)）。

# 人工修订层（异常兜底）

自动提取的准确率已由跨源校验背书（同一天两份日报逐值一致），因此人工不参与日常录入，只在**异常时兜底**：某字段 OCR 出错或置信度低时，管理员在数据表里就地改掉，不必等发版修提取器。

## 数据模型

`gd_spot_metric` 增加三列：

| 列 | 说明 |
| --- | --- |
| `origin` | `ocr`（自动）或 `manual`（人工修订过） |
| `edited_by` | 修订人（当前取会话角色） |
| `edited_at` | 修订时间 |

老库通过 `ALTER TABLE ADD COLUMN` 幂等补齐（`pragma_table_info` 检测列是否存在；非 sqlite 静默跳过）。

## 审计

`gd_spot_metric_audit` 记录两类事件：

| operation | 触发 |
| --- | --- |
| `edit` | 人工修订：旧值 → 新值、操作人 |
| `confirm` | 人工确认预填：值不变，标记为已复核 |
| `overwritten_by_extract` | 重跑解析覆盖了人工值：人工值 → OCR 值 |

## 重跑语义：以 OCR 为准，但不静默丢人工判断

用户明确选择「重跑一律以 OCR 为准」。实现上仍保留两条护栏：

1. 删除该日报指标**之前**，先把 `origin=manual` 的行写入审计（`overwritten_by_extract`）
2. 重跑结果里逐条产出告警：`重跑覆盖人工修订：运行日 X 对象/指标（来源）人工值 A → OCR 值 B`，页面以告警条呈现

若本次 OCR 未提取到该字段，告警写作「本次未提取到」，避免误以为值变 0。

# 图片类数据：地市节点电价档位（CV 采样预填）

图2-1（统调负荷高峰时刻）与图2-2（低谷时刻）是 choropleth 地图，数值只存在于像素里，OCR 取不到。方案：**图例色板 + 城市标签窗口采样**，预填后由人工确认（`origin=cv`）。

## 采样算法

1. **色板（随图读取，不写死）**：图例标签形如 `[-inf,200) … [800,+inf)`。在标签左侧按图像宽度比例（`30…78 × W/2381`）逐个候选取一条竖线扫描，切出「有饱和度」的连续色块；要求色块数 == 图例项数且颜色互异 → 得到档位文本 → RGB。
   - 为什么按比例：09-18 是 1587 宽，色块偏移量与 2381 宽不同，固定像素偏移会扫到白缝
   - 为什么要筛同列：OCR 会把表格里以 `[` 开头的单元格（实测 `[1717.42`）当图例项，导致色板错位
2. **城市色**：地市标签窗口内「有饱和度且非黑」的众数颜色及其占比（窗口 = 标签尺寸 × 1.45/1.75 + 边距）
3. **匹配**：颜色需贴近色板某档（RGB 欧氏距离 < 40）且占比 ≥ 0.6，否则判为不确定，**留空待人工**

## 两段匹配（预填为主，人工只做确认）

产品定位是「OCR/CV 预填为主，人工复核确认」，因此配色不一致时**不能直接留空**：

1. **严格 RGB 匹配**（距离 < 40）：图例色板与地图填充一致时使用，置信度 = 采样占比
2. **色相回退**：配色不一致时按色系（绿/蓝/黄/橙/红）匹配 —— 两套配色只有饱和度与明度不同，色系一致；置信度打折（×0.7）并给出「该图填充色与图例色板不一致，N 个地市档位由色系推断」告警

两段都要求采样占比 ≥ 0.6（标签跨在色块边界上时留空）。

实测依据：2026-09-18 那篇图例是浅色系、地图填充是饱和红 `(255,0,0)`/纯黄/蓝。严格匹配 0/6，色相回退后 **6/6（高峰）与 9/10（低谷）**，且三篇的「高峰 ≥ 低谷」自检零违例，09-19/09-21 结果完全不变。

## 离线验证（三篇真实日报，人工确认前）

| 日报 | 高峰图识别 | 低谷图识别 | 单调性违例（高峰 < 低谷） |
| --- | --- | --- | --- |
| 2026-09-21 | 10/10 | 14/14 | 0 |
| 2026-09-19 | 10/10 | 14/14 | 0 |
| 2026-09-18 | 0/6（配色不一致，正确拒填） | 0/10（同上） | 0 |

跨分辨率色板一致性：三篇读到的色板完全相同（`(183,214,163) (173,205,234) (255,255,126) (255,224,126) (255,126,126)`）。

**自检规则**：同一地市 `高峰档位 ≥ 低谷档位`，违反则告警「地图采样可能有误，请人工确认」。三篇实测零违例——这是没有 ground truth 时最强的正确性证据。

## 存储与展示

- `dataset = node_price_peak / node_price_valley`，`scope = 地市名`，`metric = 价格档位`，`value = 1..5`

# 批量重跑解析

解析器或映射逻辑升级后，历史日报不会自动更新（实测教训：v1.0.16 的 origin 映射缺陷
只影响当时已入库的日报，v1.0.17 修好后必须重跑才生效）。因此提供按区间批量重跑。

## 形态

- `POST /api/spot-report/extract/batch {from, to}`（admin）：**后台任务**，立即返回任务 id。
  每篇要跑 4 页 OCR（约 6-10 秒）+ 地图采样，同步执行会顶着 HTTP 超时
- `GET /api/spot-report/extract/batch/status?id=`（admin）：查进度（留空取最近一次）
- 串行执行：OCR 服务只有 2 个并发槽，并发重跑会把宿主机 CPU 打满并拖慢 lems 自身
- 内存任务表保留最近 5 个任务；同一时刻只允许一个批量任务

## 默认跳过「已全部人工复核」的日报

批量重跑的本意是「解析器升级后回填历史」，但顺手清掉别人已复核的状态是意外副作用
（实测发生过：一次批量重置了 24 项确认，值虽未变、「已复核」状态丢失）。因此：

- 判定：`cv == 0 && manual > 0` → 已全部复核，**默认跳过**；还有 `cv` 说明没复核完、或完全没有人工状态（未解析/只有 ocr 值）→ 可重跑
- 启动前先预览：`POST .../batch {dryRun:true}` 返回「将重跑的日期」与「跳过（已复核）的日期」，前端据此二次确认
- 需要覆盖时显式传 `includeConfirmed: true`（前端二次确认即视为勾选）
- 任务进度与完成汇总里都带上跳过列表

## 进度字段

total / done / succeeded / failed / current / errors / **overwritten** / startedAt / finishedAt

`overwritten` 是本次重跑覆盖掉的人工值条数 —— 语义仍是「以 OCR 为准」（按使用者选择），
但覆盖前逐条写审计（`overwritten_by_extract`），批量任务在结束时把条数报给使用者，
并在启动前的确认弹窗里明确提示「已人工确认或修订的值会被覆盖」。

## 前端

「信息管理」头部新增「批量重跑解析」：范围默认取已采集的最早/最新日报日，
确认后启动任务并每 2.5 秒轮询，进度显示在标题旁的胶囊里（`重跑 1/3（2026-09-19）`），
完成后弹窗汇总成功/失败/覆盖条数。

## 覆盖计数的实现教训

告警前缀「重跑覆盖人工修订」最初用 `w[:7]`（字节切片）判断，中文被切断 → 永远匹配不上，
覆盖数恒为 0。现改为共享常量 `OverwriteWarningPrefix` + `strings.HasPrefix`，并有单测锚定。

# 首页数据视图（默认视图）

首页「电力现货」区块改为双视图：**默认「数据」，可切「原图」**（页签与详情弹窗一致）。
设计取舍与理由：

- 运维看数字比看图快，原图退居「核对证据」；但**数据只在当日快照维度做图**，
  不同运行日不混画：实时成交电价的运行日是 T-2，图表标题各自标注运行日
- 图表类型按数据形态选：
  | 数据 | 形态 | 呈现 |
  | --- | --- | --- |
  | summary 正文摘要 | 当日 5 个标量 | KPI 数字条 + 环比箭头 |
  | day_ahead_trade / realtime_trade | 4 类对象 × 最高/最低/平均 | 分组柱状（按运行日分两张图） |
  | day_ahead_decl | 容量 + 占市场比例 | 堆叠条 + 图例 |
  | node_price_peak / valley | 21 地市 × 档位 1..5 | 色块网格（与日报图例同色）+ 档位说明 |
  跨日趋势折线本期不做：每天只有 1 个点，且同一运行日会被多篇日报写入，需要先去重
- **三态提示**（避免把预填当可信数据）：无数据 → 空态 + admin「去解析」；
  有 `cv` 待确认 → 顶部「待确认 N 项」徽标 + admin「去确认」，KPI 环比做视觉降权；
  全部 `manual` → 正常展示
- 卡片高度：数据视图约 500px、原图视图约 610px，切换时高度变化，首页整体仍纵向滚动

## 踩坑：失败重试打出的无限请求

首页数据视图最初按「`dataDate !== 当前日期` 就重新加载」实现。一旦 `/data` 请求失败
（`dataDate` 永远为空），每 1.2 秒一次的 `sync()` 重渲染都会再发一次请求 —— 无限重试。
这个缺陷是在本地 harness 里被卡死的页面暴露出来的。

现改为「**同一日期只尝试一次**」：`dataAttempted` 记录已尝试的日期，失败则进入错误态
（显示原因 + 「重试」按钮）；解析/确认/修订/批量重跑后用 `invalidateHomeData()` 主动失效，
切换日期也重置。这样渲染循环与请求解耦，不再有隐式重试。

# 采集后自动解析 + 首页非最新提示

## 采集后自动解析（默认开启）

每天两步（采集 → 解析）压成一步：`Collect` 落库成功后异步触发 `ExtractReport`。

- **异步**：4 页 OCR 约 6-10 秒，不能挂在采集请求上；goroutine 用独立 `context.Background()`，
  因为请求结束后原 ctx 会被取消
- **失败不影响档案**：自动解析失败只写 Warning 日志，图片档案照旧；首页数据视图会显示
  「去解析」入口，信息管理里也能手动重跑（或按区间批量重跑）
- **可关闭**：`SPOT_AUTO_EXTRACT=off/false/0/no` 时跳过（便于排障或节省 CPU）

## 首页「非最新」提示

首页默认展示「昨天」的运行日；若昨天没有日报（未发布或未采集），会退回最新一篇。
此时卡片上标注「非最新：数据截至 X」，避免把旧数据当成当日数据读。
判定在前端做（比较当前展示的运行日与本地昨天），后端不需要额外字段。

# 复核状态机：解析结果先「待确认」，人工确认才算数据可用

新版把「解析完即生效」改成「解析 → 待确认 → 人工审阅确认 → 已确认」。动机：
自动提取的正确率虽然由交叉校验背书，但**解析动作本身会覆盖昨天已核对过的判断**，
使用者需要一个「先看后认」的闸门，而不是解析完直接当可信数据。

## 状态定义（不新增列，复用 origin 三态）

| origin | 含义 | 页面 |
| --- | --- | --- |
| `ocr` | OCR/模板直接提取的表格与正文值 | 待确认 |
| `cv` | 图2-1/2-2 地市档位图像采样预填 | 待确认（另标「预填」） |
| `manual` | 已人工确认（一键确认或单值修订过，记 `edited_by`） | 已确认 |

**待确认 = `origin != 'manual'`**（含老库遗留的空串）。

与旧版最大的差异：OCR 表格值过去是「隐式可信」，不参与确认（只有 `cv` 进待确认）；
现在同样进待确认。代价是每天解析后首页会显示「待确认 82 项」，管理员需要点一次确认；
收益是复核状态终于有明确含义——`manual` 即「人看过」，且这个状态会被后续解析保护。

## 两条配套行为（缺一个状态机就漏）

1. **`ConfirmMetrics` 确认所有未复核项**（`origin != manual`，含 `ocr`）。
   旧实现只翻转 `cv`，导致整篇确认后 `ocr` 行永远无法进入「已确认」，状态无处存放。
   `dataset` 过滤保留，故「确认整篇」与「确认本表」都在。审计 `old_origin` 记原始 origin。
2. **`ReplaceMetrics` 默认保留已确认行**（`force=false`）：已确认行不删、不覆盖，
   本次解析重新提取到的同键值直接丢弃并计入 `Preserved`；删除时用 `WhereNotIn(id)` 跳过它们。
   只有 `force=true` 才「以 OCR 为准」覆盖，覆盖前逐条写审计（`overwritten_by_extract`）。

## 再解析的语义

| 场景 | 行为 |
| --- | --- |
| 信息管理「解析数据」 | `force=false`：未复核项重算，已确认项原样保留；返回 `preserved` + `pending` |
| 采集后自动解析 | `force=false`（覆盖采集同一天也保留已确认） |
| 批量重跑，默认 | 跳过「全部已确认」的日报；其余按 `force=false` 重跑 |
| 批量重跑，勾选「包含已复核」 | `force=true`：覆盖已确认值（这是当前唯一的强制覆盖入口） |

`skipConfirmedReport(pending, confirmed)` 判定改为 **`pending == 0 && confirmed > 0`**。
旧判定是 `cv == 0 && manual > 0`；把 `ocr` 也算未复核后，它会把
「58 项 ocr 未确认 + 24 项已确认」的日报误判为已复核而跳过重跑（回归用例已锚定）。

## 界面

- **信息管理列表**：新增「复核状态」列（`待确认 N 项` / `已确认 N 项` / `未解析`），
  待确认时多一个「审阅」按钮 → 直接打开该日报的「数据」页签；解析完成后自动打开审阅。
  状态数据来自 `CountMetricsByReport`（一次 `GROUP BY report_date, origin`，不做 N+1）。
- **数据表**：未复核项在顶部提示「其中 N 项尚未人工复核」，每张表标题行给「确认本表 N 项」，
  页首给「确认全部 N 项」；`manual` 单元格显示「已确认·操作人」；`cv` 单元格显示「预填」。
  OCR 值不逐格打标（一张表几十格，噪声大于信息量），未复核状态在表级提示里体现。
- **前端口径只留一处**：`isPending(m) = m.origin !== "manual"`，首页徽标 / 数据页提示 / 状态列共用
  （此前 `origin === "cv"` 在 3 处各写一遍，改一处漏一处就会漂）。
